# 技術文書の表記

## 編集手順

1. 作業対象リポジトリや対象文書、LLM Wikiに、用語集、略語一覧、表記規則、スタイルガイドがある場合は、文書修正前に参照する。
2. 用語の意味、略称、推奨表現、避ける表現が定義されている場合は、それを正とする。スキル本文の例より、対象プロジェクトの用語集・表記規則を優先する。
3. 表、コードブロック、図、見出し、入力/出力一覧などの構造化された範囲を見分ける。
4. ユーザーが表記統一または表示改行の確認を明示していない限り、本文領域だけを修正する。
5. 既存の用語、大小文字、バッククォート、技術的な意味を保つ。
6. 変更範囲は読みやすさのための表記修正に絞り、無関係な内容を書き換えない。

## 識別子の分類語

本文では、RTLの信号名や状態名、機能ID、制御値、設定値などの識別子を、分類が分かりにくいまま直で書かない。

- 信号名: 信号`tx_en_i`
- 状態名: 状態`RX_ERROR`
- 機能IDまたは機能ブロック: 機能FS-010
- 制御値: 制御値`duplex_full`
- 設定値: 設定`full-duplex`

識別子の種類に合わせて、自然な日本語の分類語を使う。代表例は `信号`、`状態`、`機能`、`制御値`、`設定`、`定数`、`ドメイン`。
最短で意味が通る表記にし、分類語の繰り返しで文が不自然になる場合は、一度だけ分類を明示する文へ書き換え、その後は自然に参照する。
同じ分類の識別子が複数並ぶ場合でも、曖昧さが残るならそれぞれに分類語を付ける。

例:
```markdown
信号`io_in`、信号`io_out`、信号`io_oeb`へ接続する。
```

### 適用する箇所

通常の文、説明段落、文章として読ませる箇条書きに適用する。特に、識別子が文の主語や目的語になる場合は分類語を付ける。

例:

```markdown
変更前: `tx_enable`が有効な場合、外部送信入力を使用する。
変更後: 信号`tx_enable`が有効な場合、外部送信入力を使用する。
```

### 適用しない箇所

構造上すでに分類が明確な箇所や、分類語の追加が表現を妨げる箇所は変更しない。

- `信号名`、`状態`、`機能名`、`定数名`、`カテゴリ`、`方向` などの列を持つ表
- 入力、出力、定数、信号、状態、機能として明示されている一覧
- `### FS-010 機能制御値解決` のように分類が分かる見出し
- コードブロック、WaveDrom、JSON、ソースコード、コマンド出力、インターフェース定義そのもの
- 分類語を足すと読みにくくなる数式やBoolean式

## タイミングの記述

機能仕様書、インターフェース仕様、タイミング仕様でクロック、クロックイネーブル、tick、pulse、valid、ready、要求、通知、完了通知を説明する場合は、信号名の語尾だけで役割を定めない。
RTLまたは設計モデルから、生成条件、消費条件、アイドル時の状態、状態遷移を確認して説明する。

信号の説明では、次の二つを分ける。

- 関係分類: 生成側と消費側の関係を表す
  - 要求: 生成側が消費側へ処理の開始、停止または切替を求める
  - 通知: 生成側で発生したイベントまたは状態を消費側へ伝える
  - 完了通知: 処理の完了を後続ブロックまたは要求元へ伝える
  - タイミング: データの取込み、更新などを行う周期を示す
- 操作分類: 信号が関与する操作を表す。開始、停止、モード移行、同期開始、位相合わせ、データ取込み、データ更新などを具体的に記述する

信号名の説明には、対象、操作、関係分類を必要な範囲で含める。

クロックそのものとクロックイネーブルは区別し、クロックイネーブルは対象クロックの遷移または対象データの取込み・更新との対応を記述する。

例:

```markdown
変更前: 受信クロック開始通知
変更後: 受信データ出力用クロック同期開始要求

変更前: 受信データ出力用クロック位相合わせ
変更後: 受信データ出力用クロック位相合わせ通知

変更前: 送信クロックの立上りに対応する1クロック幅イネーブル
変更後: 送信データ取込みタイミング。信号`tx_clk_o`の立上りと同じ周期に1クロックHighになる信号
```

## Markdownの表示改行

Markdownで表示上の改行が必要な本文段落では、改行したい行の末尾に半角スペース2つを入れる。

例:

```markdown
本章は外部評価時の電源および信号電圧条件を定義する。  
RTL上では電圧レベルを直接表現せず、トップレベルI/O制約および評価環境の条件として扱う。
```

箇条書き、見出し、表、コードブロックには、表示改行用の半角スペース2つを追加しない。
WaveDrom、JSON、ソースコード、コマンド出力も変更対象に含めない。
空行などで既に表示上の区切りがある箇所には追加しない。
同じ項目の中で説明を分けたい場合は、必要に応じて子項目へ分けるか、通常の継続行としてインデントする。

例:

```markdown
- クロックドメイン: PHY内部処理ドメイン
  入力同期はクロック・タイミング仕様で定義する
```

## 冗長表現の扱い

- 同じ意味の説明を言い換えて繰り返さない。各文には新しい情報を持たせる
- 見出し、項目名、括弧内の説明で伝わる内容を、直後の説明で繰り返さない
- 「処理を実行する」のように短く言える表現は「処理する」にする。ただし、対象、条件、技術的な意味を変えない
- 「基本」「標準」「一般的」などの修飾語は、技術標準、仕様、規格、既存設計、測定条件などの明確な参照元に基づく場合だけ使う

短縮すると対象、条件、例外、因果関係が曖昧になる説明は残す。
定義済みの詳細を参照する場合も、その箇所の理解に必要な役割や振る舞いは記述する。

## 内部構成の記述

内部構成では、実装上の個別レジスタ、カウンタ、ラッチを列挙する前に、機能上の役割が分かる回路単位で記述する。
同一文書に同種の機能記述がある場合は、先にそれらを確認し、項目構成と詳細度をそろえる。特定の実装箇所だけを、信号の組合せ、更新順序または条件式まで展開しない。

記述する際の注意点

- 個別のレジスタ、カウンタまたはラッチは、ビット幅、保持期間、段数または更新順序が仕様上の制約となる場合だけ記述する。
- 組合せ回路の選択条件、順序回路の更新条件、状態機械の状態および遷移条件は、内部構成ではなく動作または状態遷移の項目で定義する。
- 状態機械と記述する場合は、状態名と遷移条件を同じ節または参照先で定義する。
- FIFOと記述する場合は、同期FIFOまたは非同期FIFOの種別を示し、必要に応じてデータ幅、深さ、書込み・読出しクロックドメインおよびfull/empty制御を記述する。FIFOの深さやデータ順序が仕様上の制約でない単なる一時保持は、順序回路によるデータ保持として記述する。
- 同期化回路と記述する場合は、同期対象、同期先クロックドメイン、同期方式および同期段数を仕様上必要な範囲で示す。複数bitデータの受け渡しは同期化回路とはせず、データの一貫性を保証するFIFOまたはハンドシェイクとして記述する。
- メモリ・RAMと記述する場合は、必要に応じてデータ幅、アドレス幅または深さ、読出し・書込みポート数、クロックドメインおよび読出しタイミングを示す。単一データの保持でアドレス指定や容量が仕様上の制約でない場合は、順序回路によるデータ保持として記述する。

例
```markdown
- 内部構成: 状態`WAIT`および状態`TRANSFER`を管理する状態機械と、出力データ信号および有効状態を示す信号を保持する順序回路
- 状態遷移: 入力データ有効信号を受けた場合に状態`WAIT`から状態`TRANSFER`へ遷移し、転送完了通知を受けた場合に状態`TRANSFER`から状態`WAIT`へ遷移する

- 内部構成: 受信nibbleを入力順に保持する同期FIFOと、FIFOの書込み・読出しおよび出力有効状態を管理する順序回路
```


## 仕様値の範囲

仕様値の範囲を記載する前に、その範囲が要求、規格、アルゴリズムまたは技術的制約から導かれることを確認する。
現行RTLの信号幅、カウンタ幅、配列長など、変更可能な内部実装からのみ導かれる値は仕様値にしない。
この場合は、必要な振る舞いを仕様として記述し、内部表現は実装側で追従できる構成とする。

## 入出力一覧の記述

入力および出力の一覧では、信号の役割を簡潔に示す。保持期間、Ackによる解除条件、状態遷移、パルス幅などの動作条件は、処理、状態遷移またはタイミングの項目に記述する。

例:
```markdown
- 入力: `error_pending_i`: 上流ブロックから受ける受信エラー通知
```

## 接続の記述

接続の項目では、接続する信号名と機能またはブロック間の関係を示す。入出力一覧で定義済みの役割や動作条件を繰り返さない。

例
```markdown
- 接続: 上流ブロックの信号`data_valid_o`を信号`data_valid_i`へ受け取り、信号`done_o`を上流ブロックへ渡す
```


## 定数の記述

機能固有の定数を記述する場合は、関連する定数を短い分類名でまとめ、定数ごとに用途を1行で示す。現行値、既定値または許容範囲が仕様上の制約となる場合だけ併記する。別の定数表が全体の正本である場合も、機能の理解に必要な定数を「RTL設計定数を参照」のような一括参照だけで済ませない。

例
```markdown
- 受信保持関連定数
  - `PATTERN_LENGTH`: パターン検出に必要な最小データ長。現行値は7
  - `FIFO_DEPTH`: 受信データを保持するFIFO深さ。現行値は64
```

## 箇条書きの分類

説明が1文で済む項目は、ネストせず、`項目: 説明文` の形で書く。
同じ分類に複数項目が属する場合、または分類内で条件、手順、例外を並べる場合だけネストする。
分類名は項目群の役割を示す短い名詞句にする。
機能仕様では、短い定型項目を先に並べ、詳細項目を後に置く。

箇条書きおよび表中の文章は、行末に句点「。」を付けない。
同じ項目または表セル内で複数の文を記述する場合は、文の区切りに句点「。」を使用してよい。

例:

```markdown
- 責務: 受信経路のローカル状態を生成し、同期成立、受信中、受信終端、受信異常を状態として表現する
- 入力: CDR状態、キャリア状態、プリアンブル検出、SFD検出、リセット状態
- 出力: 受信状態、受信同期成立通知、受信終端通知
- 内部構成: 同期成立、受信中、受信終端および受信異常を管理する状態機械
- 状態: 状態`RX_IDLE`、状態`RX_SYNC`、状態`RX_ACTIVE`、状態`RX_ERROR`
- 状態遷移
  - 信号`rx_enable`がLowの場合、受信状態を状態`RX_IDLE`へ戻す
  - SFD検出通知を受けた場合、受信状態を状態`RX_ACTIVE`へ遷移させる
```

ただし、信号一覧、状態一覧、値一覧のように表にした方が比較しやすい場合は、ネストした箇条書きではなく表を優先する。
既に見出し、表、ラベル付き一覧で分類が明確な箇所は、無理にネストしない。

## 曖昧表現の扱い

仕様本文では、読み手が実装、検証、接続、判定条件を一意に決められない表現を放置しない。

代表的な曖昧表現は以下とする。

- 「既知の」「所定の」「規定の」
- 「主要な」「必要な」「十分な」「最小限の」
- 「適切に」「安全側に」「通常の」「基本の」
- 「など」「任意の」「できる」「可能」

これらを見つけた場合は、次の優先順位で処理する。

1. 詳細を定義した章、表、定数、状態表、信号表、用語集が同じ文書または関連文書にある場合は、その定義名と参照リンクへ寄せる。
2. 参照先がない場合は、その場で具体値、信号名、状態名、条件、列挙、範囲、初期値、優先順位、または保持動作を書く。
3. 表や一覧で既に定義済みの内容を本文に重複展開しすぎない。本文には「何をするか」と参照先を書き、詳細は定義表を正とする。
4. 要求レベルの可否を表す `必須`、`任意`、機能要否の `R`、`O` のように、文書内で意味が定義されている語は残してよい。
5. 技術標準名や既存インターフェース名に含まれる語は、意味が一意なら無理に置き換えない。

例:

```markdown
変更前: 既知のMII nibble列を生成する。
変更後: [テストパターン](#テストパターン)で定義するMII nibble列を生成する。

変更前: 規定期間入力遷移を検出しない場合にキャリアロスとする。
変更後: 定数`carrier_loss_cycles`で定義する期間、入力遷移を検出しない場合にキャリアロスとする。

変更前: 制御矛盾時は安全側の制御値を配布する。
変更後: 制御矛盾時は直前に確定した制御値を保持し、信号`control_conflict_error`を通知する。
```
